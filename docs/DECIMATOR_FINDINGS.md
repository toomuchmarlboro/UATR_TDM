# Decimator and network migration — findings, decisions, and bugs

Written 2026-09-08, covering the work that added on-FPGA 4× decimation and moved
the array from `192.168.1.x` to `192.168.3.x`.

This is the record of **what was wrong and why**, not a how-to. For procedures
see `docs/DECIMATION.md`, `docs/NETWORK_SETUP.md` and `docs/CHANGING_IP.md`.

---

## 1. The design brief, and how it changed

The original request was a **CIC decimator**, N=3, R=4, 16 parallel instances,
inserted after the TDM16 merge. Three of that spec's premises turned out to be
wrong, and each changed the design.

### 1.1 A CIC cannot do this band

The band of interest is **10 Hz – 11 kHz**, which is 92% of the 12 kHz Nyquist
after a ÷4. That is a brick-wall requirement, and a CIC is the bluntest filter
there is:

| frequency | role | CIC N=3 response |
|---|---|---|
| 11 kHz | top of the band | **−9.2 dB** droop |
| 13 kHz | folds onto 11 kHz | **−13.3 dB** |

A 13 kHz tone would land on top of the 11 kHz signal only 4.1 dB below it.
Raising the order makes it *worse* — N=5 gives −15.3 dB of droop at 11 kHz —
because the CIC's first null is pinned at 24 kHz and no choice of N moves the
transition down.

A CIC would have been correct for the 100–1500 Hz band the spec's context
section described. It is wrong for 11 kHz.

**Decision: two cascaded halfband FIR stages**, 96k → 48k → 24k. Halfband
because every even tap except the centre is exactly zero (halves the
multiplies), and linear phase because the coefficients are symmetric (halves
them again).

### 1.2 Sixteen parallel instances do not fit

The spec assumed "EP4CE6 has LE budget to spare". The shipping build was
already at **4,025 of 6,272 LEs with 3,047 registers**. Sixteen parallel CIC
instances at 30-bit accumulators need ~274 flip-flops each — 4,384 registers,
against 6,272 total on a device where Cyclone IV E has **one flip-flop per LE**
and no LUT-based distributed RAM.

**Decision: one time-multiplexed datapath.** `tdm16_valid` fires once per audio
frame, which is **256 clock cycles** at 24.576 MHz — ample time to sequence 16
channels through shared arithmetic. This spends the multipliers (0 of 30 used)
and M9K (3% used) that were idle, instead of the LEs that were nearly gone.

### 1.3 No slot decoder or encoder is needed

The spec called for a slot-decoder and slot-encoder around the filter array.
Neither exists, because `tdm16_merge` (`rtl/tdm16_merge.vhd:65`) emits a **flat
384-bit parallel register** with a one-cycle strobe, and `packet_formatter`
consumes exactly that. The decimator is a drop-in with identical ports on both
sides.

Channel alignment — the spec's GCC-PHAT concern — is preserved structurally:
all 16 channels are written on the same strobe and read by the same schedule.

### 1.4 Also corrected

- **"TDM16 merge is mid-verification in ModelSim"** — it is in the shipping
  build and running on hardware. Its one real bug (level test instead of edge
  detect, firing 128×/frame) was fixed in `927aac7`.
- ⚠ **Naming collision:** `tdm16_merge` is active; `tdm16_rx` is a *board-level*
  config requiring the R21/R122 jumper and is **not** active. Do not confuse
  them.

## 2. Filter design

Coefficients are generated by `python/design_decimator.py`, which also emits the
VHDL package and bit-exact reference vectors. Lengths were chosen by exhaustive
search over (n, beta) for the cheapest pair meeting spec.

```
stage 1   n=27,  beta 11.0   15 non-zero taps    8 folded
stage 2   n=171, beta 11.0   87 non-zero taps   44 folded
```

Measured on the **quantised** cascade, not the float ideal:

```
passband ripple 0-11 kHz      0.00015 dB      (limit 0.01)
droop at 11 kHz              -0.0001  dB
worst alias band             -102.5   dB      (limit -100)
at 13 kHz                    -120.3   dB
group delay                    1.91   ms
```

### Why 100 dB, without measuring the water

The stopband was sized against the **ADAU1978's own noise floor** (103 dB
dynamic range, `docs/adau1978.pdf` p.3) rather than against a measured spectrum.
At −102.5 dB, aliased content lands under the converter's noise and cannot
degrade anything, whatever is actually up there.

This was deliberate: no WAV capture was available, and designing to the noise
floor is assumption-free. The cost is ~26 more taps than an optimistic design,
against 2.5× MAC headroom — not worth a bench session to reclaim.

**The compensation FIR is unnecessary.** 0.0001 dB droop at 11 kHz. That was
listed as an open question in the original spec; it is answered.

### Scope boundary

At 12 kHz the response is only −6 dB. This filter protects the **band of
interest**, not the full 0–12 kHz output band. If the application ever widens
toward the new Nyquist, the design must be revisited.

## 3. Bugs found

Ordered by severity. Every one of these would have shipped.

### 3.1 Pipeline misalignment — silently wrong output ★ worst

Stage A registered the RAM data **and** the coefficient together, but stage B
read the coefficient through a *second* register (`cf1` → `cf1_d`) while
reading the data through only one. **Every coefficient multiplied the wrong
sample.**

```
as-written : maxdiff vs direct convolution = 1,243,545,140
corrected  : maxdiff                       = 0
```

**Why it nearly shipped:** my first verification modelled the pipeline I
*intended*, not the one I *wrote*. It was only caught by building a model that
follows VHDL signal semantics exactly — every signal read returns its pre-edge
value — and comparing against a direct convolution.

Synthesis passes. Timing passes. TNS is 0.0. It would have appeared as noise on
all 16 channels after flashing, with nothing in the toolchain flagging it.

### 3.2 Schedule overrun — dropped output frames

The cycle budget assumed 1 cycle per tap. The `ADDR → MAC` state machine as
written took **2**:

```
engine 2 needed  16 ch x 44 taps x 2 cycles + overhead = 1,440 cycles
budget                                                  1,024 cycles   (141%)
```

`e2_go` is a one-cycle pulse; if engine 2 is still busy it is **missed
silently**. Output frames vanish, `valid_out` stutters, and there is no error
anywhere — it would have looked like intermittent network packet loss.

Fixed by pipelining both engines to one tap per cycle:

```
engine 1:  144 cycles of  512  (28%)
engine 2:  720 cycles of 1024  (70%)
```

### 3.3 `mod` on a non-power-of-two inferred a hardware divider

`D2` was briefly 192, and `mod D2` synthesised into two `lpm_divide` instances
— **282 LEs** of real divider on a device with none to spare. Replaced with a
conditional subtract (one comparator).

The RTL now carries a `NEVER WRITE "mod D2" HERE` comment.

### 3.4 Memory blocks, not memory bits, are the binding resource

Padding `D2` from 171 to 256 costs nothing in LEs and **11 extra M9K blocks**.
At 24-bit width an M9K holds only 256 words, so the design can exhaust all 30
blocks while showing 60% *bit* utilisation. The fit failed at 60% memory bits.

Fixed by using exact depth (171) with an explicit wrap.

### 3.5 SignalTap was in the deployment images

`ENABLE_SIGNALTAP` was `ON` with `signaltap_rmii.stp`, and its capture buffer
consumed the M9K blocks the decimator needed. **The fit only succeeded after
removing it.**

It is a debug instrument and should never have been in shipping images. Note
the pre-existing 96 kHz NODE images were built *with* it.

### 3.6 Multiple constant drivers

`saturated` was written from both engines. Quartus rejects this outright
(`Error 10028`), which is correct behaviour — split into `sat1_r`/`sat2_r`
OR-ed combinationally.

### 3.7 Host: rate detection false-positive under heavy loss

Loss only ever *lowers* the measured packet rate, and the two rates are exactly
4× apart. A 96 kHz board losing 75% of its packets measures 24,000 and was
reported as a **healthy 24 kHz board, "confident"**.

Fixed using the sequence numbers, which are loss-independent — the FPGA
increments them per packet *sent*:

```
96 kHz board, 75% loss:
  without seqs -> (24000, True)   wrong
  with seqs    -> (96000, True)   right
```

### 3.8 Host: two `check_sync.py` guards had silently died

The IPv4 checksum check and the header-length check were both regexing for
literals (`IP_CHECKSUM`, `when 16 => x"..."`) that had become computed
expressions in earlier work. **They had been passing by not matching anything.**

Rewritten to read the current RTL. The new `C_DECIMATE` check immediately
caught a real mismatch, proving it works.

### 3.9 Host: standalone GUI generator ordering

`SUBNET` was added to `ctrl.py` but not to the generator's `ct_names` list, so
`FPGA_IP = SUBNET + ".101"` ran before `SUBNET` existed — `NameError` on
import. Later the same pattern recurred with `detect_rate`, which imported fine
and would have raised `AttributeError` the first time a meter updated.

The file already carried a comment warning about exactly this ordering trap for
`buoy_ip`/`BUOYS`.

### 3.10 Build races produce mislabelled images

Two concurrent build scripts both edit `rtl/top_system.vhd` and both write
`output_files/TDM_UATR.sof`, so the `.jic` copied out can carry another run's
`C_NODE` — an image labelled for one board containing another board's IP.

`build_all.sh` now takes a lock and refuses to start if one is held.

## 4. Network migration findings

### 4.1 `INADDR_ANY` does not mean "any destination"

Measured on this machine:

```
destination        host owns it?     received on INADDR_ANY socket?
127.0.0.1          yes               YES
192.168.1.10       yes               YES
192.168.3.240      yes               YES
192.168.3.10       NO                NO      <-- silently dropped
```

Unicast UDP is filtered by **destination address**. The kernel drops packets
addressed to an IP the host does not own, before any socket sees them. The
sender's subnet is irrelevant.

**Consequence:** the host must hold an address matching each image's
compiled-in `C_PC_IP`. A board on `192.168.3.101` sending to `192.168.3.10`
delivers nothing until the host owns `192.168.3.10`.

### 4.2 `C_PC_IP` must move with the boards

It is load bearing twice: it is where audio is sent, **and** it is the filter
deciding whose ARP the board will learn from (`pc_mac_r`). Changing only the
board addresses gives four boards transmitting perfectly into nothing.

### 4.3 The checksum assertions are pinned to the subnet

The IPv4 header checksum is computed at elaboration by `net_pkg.ipv4_checksum`
and follows automatically. But the **static assertions that verify it** carry
expected values that must be recomputed by hand.

Confirmed they bite: corrupting node 1's expected value produces
`Error (10652): VHDL Assertion Statement ... assertion is false` and stops the
build.

Old set `B577/B576/B575/B574` → new set `B177/B176/B175/B174`. They differ by
exactly `0x0400`, the third octet's contribution — a cheap sanity check.

### 4.4 Capacity is not close to a limit

```
4 boards @ 24 kHz + 4 buoys telemetry = 46.6 Mbit/s   (4.7% of gigabit)
4 boards @ 96 kHz + telemetry         = 183.6 Mbit/s  (needs gigabit)
```

Telemetry is 0.9 Mbit/s — under 2% of the audio. It was never a constraint.

Decimation is what takes the array from *needs gigabit end to end* to *fits in
100BASE-TX*.

### 4.5 Python is fast enough — but only if batched

Measured:

```
socket receive, 64 MB rcvbuf              59,650 pkt/s   0.00% loss
four sockets, four senders, 12,000 pkt/s   0.0000% loss

full 24-bit unpack, ONE packet at a time   30,800 pkt/s   <-- below 48,000
batched numpy (1000 packets at once)      161,000 pkt/s
```

**A naive loop that unpacks each datagram as it arrives drops packets at
96 kHz.** The rule for the deployment app: *receive into a list, never unpack
inside the receive loop, unpack in vectorised batches.*

`udp_monitor.capture()` already does this. Preserve the structure.

## 5. Verification, and its limits

**There is no simulator.** GHDL is not installed, and the bundled Questa fails
with `Unable to checkout a license`. So the verification path is:

1. **Quartus static assertions** — evaluated at elaboration, fail the build.
   Proven to work by deliberate corruption.
2. **`python/design_decimator.py --check`** — re-measures ripple and alias
   rejection against the stated limits.
3. **Cycle-accurate Python model** — follows VHDL signal semantics exactly
   (every signal read returns its pre-edge value). This is what caught the
   pipeline misalignment.
4. **`sim/decim_ref_vectors.txt`** — bit-exact reference output from the same
   script that generates the coefficients, so they cannot drift apart.
5. **`python/check_sync.py`** — 58 assertions cross-checking host constants
   against the RTL.

### What is NOT verified

**Nothing has been on hardware.** The decimator is verified numerically and
structurally only. The first capture is the real test, and the reference
vectors exist so it can be diffed rather than eyeballed.

Read the **packet rate first**: ~3,000/s is success; ~12,000/s means
`valid_out` is being ignored downstream — the classic decimator integration
bug, not a filter fault.

## 6. Standing lessons

1. **Model what you wrote, not what you meant.** The pipeline bug survived one
   round of "bit-exact" verification because the model encoded the intent.
2. **A passing check may be checking nothing.** Two `check_sync.py` guards had
   been green for weeks while matching no text at all.
3. **Cheap in one resource is expensive in another.** Padding a RAM depth costs
   zero LEs and broke the fit on memory blocks.
4. **Generated files must be executed, not just generated.** "wrote 3,290
   lines" is not evidence; two separate namespace bugs only appeared on import
   and on first use.
5. **Never `git checkout` a file mid-session to reset unrelated state.** It
   reverted the entire subnet migration and had to be reapplied by hand.
