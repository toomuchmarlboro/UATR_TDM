# Ethernet Transmission

## Purpose

The FPGA streams 16 channels of 24-bit audio from the ADAU1978 ADCs to a host PC using Ethernet over UDP. The Cyclone IV FPGA creates the Ethernet frame and sends it to a LAN8720A PHY through RMII. The PHY then converts the digital RMII stream to 100BASE-TX Ethernet for the media converter and subsea fiber link.

```text
ADAU1978 ADCs
    |
    v
TDM8 receivers
    |
    v
packet_formatter
    |
    v
Async FIFO
    |
    v
udp_tx_core: Ethernet + IPv4 + UDP headers
    |
    v
rmii_tx: preamble + frame data + FCS + IFG
    |
    v
LAN8720A PHY
    |
    v
RJ45 -> media converter -> single-mode fiber -> host PC
```

## Data Rate

The active design carries:

| Item | Value |
|---|---:|
| Audio channels | 16 |
| Sample size | 24 bits |
| Sample rate | 96 kHz |
| Audio payload rate | 36.864 Mbps |
| Ethernet link | 100 Mbps RMII/100BASE-TX |
| UDP destination port | 5005, configured per board |
| Payload per UDP packet | 410 bytes |
| Audio frames per packet | 8 |
| Packets per second | approximately 11,950 to 12,000 |

The 100 Mbps link provides approximately 2.7 times the raw audio payload bandwidth required by the 16-channel stream.

## 1. Audio Packet Formation

`packet_formatter.vhd` runs in the audio-side clock domain. Each valid TDM sample is latched and written into an asynchronous FIFO one byte at a time.

A complete UDP payload contains eight audio frames:

```text
8 frames x 50 bytes per frame = 400 bytes
10-byte packet header          =  10 bytes
                                  -------
                                  410 bytes
```

Each 50-byte audio frame contains:

```text
bytes 0-1    diagnostic/status bytes or frame information
bytes 2-49   16 channels x 3 bytes per 24-bit sample
```

The first ten bytes of each packet include a project magic value and a 32-bit sequence number:

| Byte range | Contents |
|---|---|
| 0-3 | Magic value `AD A1 97 78` |
| 4-7 | 32-bit packet sequence number, most significant byte first |
| 8-9 | Diagnostic bytes |
| 10-409 | Eight 50-byte audio frames |

When all 410 bytes have been written, `packet_formatter` toggles `packet_ready`. The toggle safely crosses from the packet-formatting clock domain to the 50 MHz Ethernet transmit clock domain.

## 2. UDP, IPv4, and Ethernet Headers

`udp_tx_core.vhd` presents a fixed 452-byte frame body to `rmii_tx`:

```text
14-byte Ethernet header
20-byte IPv4 header
 8-byte UDP header
410-byte UDP payload
--------------------------------
452 bytes before Ethernet FCS
```

The Ethernet header contains:

| Field | Size | Description |
|---|---:|---|
| Destination MAC | 6 bytes | PC MAC address |
| Source MAC | 6 bytes | FPGA MAC address |
| EtherType | 2 bytes | `0x0800`, IPv4 |

The IPv4 header is configured as:

| Field | Value |
|---|---|
| Version / header length | IPv4, 20-byte header (`0x45`) |
| Total length | 438 bytes: IPv4 header + UDP header + payload |
| Flags | Do not Fragment |
| TTL | 64 |
| Protocol | UDP (`17`) |
| Source address | FPGA IP address |
| Destination address | Host PC IP address |
| Header checksum | Computed from the configured addresses and length |

The UDP header uses the configured board port as both source and destination port. The UDP length is 418 bytes:

```text
8-byte UDP header + 410-byte payload = 418 bytes
```

The UDP checksum is set to zero. For IPv4, zero indicates that the UDP checksum is unused. Ethernet still protects the complete frame with its FCS.

## 3. RMII Transmission

The LAN8720A receives RMII data from `rmii_tx.vhd` on a 50 MHz reference clock. RMII transfers two bits per clock, giving:

```text
50 MHz x 2 bits = 100 Mbps
```

The transmit state machine sends each byte as four 2-bit slices, least-significant slice first:

```text
byte[1:0] -> byte[3:2] -> byte[5:4] -> byte[7:6]
```

`rmii_tx` generates the standard Ethernet framing sequence:

1. Seven bytes of preamble, all `0x55`
2. One-byte Start Frame Delimiter, `0xD5`
3. The 452-byte Ethernet/IP/UDP frame body
4. Four-byte Ethernet FCS generated by the CRC32 block
5. Inter-frame gap of at least 96 bit times

`rmii_tx_en` remains asserted during the preamble, SFD, frame body, and FCS. It is deasserted during the inter-frame gap.

The transmit handshake is intentionally level-based:

- `tx_start` is held high for the complete frame body.
- `tx_ready` acknowledges that the current `tx_data` byte has been consumed.
- The producer must place the next byte on `tx_data` before the next acknowledgement.
- The transmitter remains busy through the FCS and inter-frame gap.

This prevents another transmitter, such as the ARP responder, from taking control of the RMII pins before the current Ethernet frame is completely finished.

## 4. PHY and Fiber Path

The FPGA does not directly drive the twisted-pair or fiber signaling. The physical path is:

```text
FPGA RMII pins
    -> LAN8720A 100 Mbps PHY
    -> 100BASE-TX RJ45 connection
    -> media converter
    -> BiDi WDM single-mode fiber
    -> second media converter
    -> host PC Ethernet interface
```

The media converters use different wavelengths for transmit and receive, so one fiber core carries the full-duplex link. The subsea cable is approximately 7 km long, while the media converters are rated for up to 20 km under the specified optical conditions.

## 5. ARP and Host Reception

Before the host can receive unicast UDP audio, the FPGA must know the host MAC address. The ARP responder listens for ARP requests and learns the sender MAC address. It can also transmit an ARP reply using the same RMII transmitter.

After address resolution, the host receives UDP datagrams on the configured port. The sequence number in bytes 4-7 allows the receiver to detect missing packets. A missing packet represents eight missing audio frames, so the host can report the gap and insert the appropriate replacement samples instead of silently shifting the rest of the stream in time.

## Verified Results

The Ethernet transmission was tested on hardware with Wireshark and the Python UDP receiver.

| Check | Result |
|---|---|
| Ethernet stack | Complete and operating on hardware |
| Packet rate | Approximately 11,950 packets/s |
| FPGA-side sequence gaps | 0 observed |
| Ethernet FCS | Confirmed valid in Wireshark |
| IPv4 checksum | Confirmed valid in Wireshark |
| UDP delivery | Audio packets received by the host |
| Physical transport | LAN8720A -> media converter -> fiber path |

The measured packet rate is consistent with the fixed packet size and the 96 kHz audio source. The zero FPGA-side sequence gaps confirm that the packet formatter, FIFO, clock-domain crossing, and transmit scheduler kept up with the audio stream during the hardware test.

## Important Limitations

UDP does not retransmit lost packets. Ethernet and IPv4 checksums identify corrupted frames, while the application sequence number identifies missing packets. The host receiver must therefore monitor sequence numbers and handle gaps explicitly.

The current transmit logic uses fixed packet and payload sizes. Changing the payload size requires the IPv4 total length, UDP length, FIFO terminator, packet parser, and checksum-related checks to be updated together.
